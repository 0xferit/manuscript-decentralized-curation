# Architecture

## Release publication

Every merge to `main` that a pull request labels `release:major`, `release:minor` or `release:patch` publishes a new Zenodo version without a human step. The version is semantic at the level of citations: a major bump means a citation of the previous version no longer matches the paper's claims. Labels, not commit types, carry that judgement because commit types here do not distinguish a changed claim from a reworded one. A push releases the highest bump among pull requests merged since the latest `v*` tag, so a superseded pending run never loses a bump, and an unlabelled merged pull request fails the run rather than skipping a release.

Review moves before the merge: each labelled pull request renders the PDF its merge would publish. After the merge, CI renders the PDF from the merged commit and binds it in a manifest to the tag, source commit, manuscript digest and PDF digest. The GitHub release holds those bytes, and the Zenodo deposit verifies and uploads the same bytes; it never renders. The tag and release assets are the frozen snapshot. `.zenodo.json` in the tagged source owns deposit metadata. Manually published GitHub releases take the same deposit path.

Each step has the narrowest credential it needs: planning reads pull requests, rendering has read-only access, only release creation can write repository contents, and the Zenodo credential reaches only the upload step after local validation. Releases and Zenodo deposits are serialized across the repository. The uploader refuses an existing unpublished draft, a conflicting published version, a version not newer than the latest, or an upload checksum mismatch; a retry after successful publication is a no-op when the PDF and descriptive metadata match. Within a run it repeats reads, uploads and deletions after rate limiting, an internal or gateway error or a dropped connection, because repeating them cannot change the result, but sends version creation and publication once; before publishing it confirms the draft holds only the uploaded PDF.

Pull-request authors and reviewers are trusted to label correctly and to inspect the rendered PDF; a mislabelled or broken merge publishes a permanent DOI. Manifest checks establish artifact identity, not scientific validity. The Zenodo account must use a single publisher: its separate GitHub integration must be disabled, and nobody may edit drafts concurrently with publication, because the legacy Zenodo API cannot atomically reserve a new draft. Failed or uncertain uploads require inspection before retrying.

## Manuscripts and application boundaries

`paper.qmd` owns the general Decentralized Curation framework and shared protocol rules. `projects/truth-post/blueprint.md` develops the news application; `projects/truth-post/implementation-report.md` records the partial 2023 deployment. `projects/rpgf/companion-paper/manuscript.md` is the current public-goods application. Historical designs and workshop demonstrations do not establish that an integrated implementation exists.

The companion cites a released foundational preprint for its research context and records the later working decisions it uses separately. Its source excerpts, source digests and publication-preparation results are historical evidence. Published snapshots and editable working sources are separate; local corrections do not change prior publication or human-verification records.

## Accuracy and eligibility

The foundational paper's Accuracy layer owns optimistic publication, bonded challenges and item closure. Structural transaction checks precede publication; semantic claims remain contestable. Closure affects the bonded item and its future eligibility, without banning its publisher or beneficiary from fresh submissions. Reputation is separate from submission eligibility.

Application funding rules distinguish prospective allocation from amounts already earned. The ongoing public-goods profile preserves earned beneficiary entitlements through disputes, revisions and closure. Neither a later assessment nor payment collection may reinterpret an earlier entitlement.

## Relevance accounting and settlement

The foundational paper's Relevance layer owns drafting, quorum, service fees, penalties, rounding and public appeal settlement. Utility-token collateral and redistribution use a ledger separate from ether (ETH) jury-service funds and appeal capital. Reference fee and workload values are defined in the paper; application documents refer to those definitions. Workload assumptions are not proof of effort, and fixed service fees do not establish truthful or competent assessment.

Each pool defines its own relevance rubric and numeric interpretation. A direct proportional funding application uses scores as relative allocation weights, subject to its eligibility and cap rules. The Truth Post feed uses its separate ranking formula. Neither allocation weights nor coherence measure public benefit directly.

Ordinary attempts already drawn before exit and funded contested appeal chains retain the continuation rights specified in the paper. Continuation preserves pinned assessments and financial commitments without restoring the closed item's eligibility. Earned jury fees, contribution refunds, backer payouts and beneficiary earnings remain distinct obligations. Unused reservations return through their original funding paths; assigned but unclaimed entitlements are not reusable funds.

The paper owns the execution-order rule for fresh service-budget reservations, the positive proof-opening window, bounded leak confiscation, exact integer allocation and recipient-controlled receiving addresses. Implementation details explicitly left open there remain open in application documents. In particular, applications must not infer an asset conversion rate or resolve unspecified same-round penalty ordering by combining ledgers or collecting collateral twice.

## Build and generated artifacts

The Makefile owns local build entrypoints. The Quarto website configuration selects the foundational paper and project publication wrappers and owns the shared page tree. Native navigation supplies a responsive document sidebar, search, section breadcrumbs and previous/next links; each article's table of contents is separate on the right. The root remains the foundational paper, with public-goods and Truth Post branches preserving existing routes. Requests to the retired public-goods design route redirect to the companion; the website publishes no copy of the retired document. The custom figure script only switches figure variants; it does not replace website navigation or theme controls.

Wrappers include their canonical project sources rather than maintaining copies. The companion wrapper declares its source directory as a resource path for bibliography resolution and uses the source's mathematical input notation. Its website rendering is a working revision separate from the frozen preprint. Analysis outputs are generated and ignored; tracked conceptual diagrams are regenerated from `diagrams/generate_diagrams.py`. The shared bibliography is `references.bib`. Shared HTML overflow rules live in `layout.css` so tables and equations can scroll within the article in both color themes.

The companion uses Pandoc with its declared bibliography and explicit mathematical-input extension. Its internal PDF link color is set in the LaTeX-only header so it cannot override the website's light and dark link colors. Secondary text uses contrast-tested theme colors without opacity reductions on metadata, callout headings or numbered section headings. Local review outputs under `outputs/` are separate from released preprints, publication records and historical artifact digests. The website pipeline publishes HTML, so it does not advertise local-only PDF files as downloads. A build verifies document production, not the economic mechanism or the completeness of human source verification.

## Continuous integration and merge gates

`main` accepts changes only through pull requests that pass two required checks on an up-to-date branch: `build-and-deploy` and `claude-review`. `build-and-deploy` runs the repository invariants, regenerates the simulations, renders the site and deploys it, as a preview for a pull request and to production for `main`. A build that renders therefore also proves the invariants hold. `claude-review` is an advisory reviewer that gates only on completing, not on its findings. Its job summary lists the tool calls Claude was denied and quotes Claude's final message, so a review that found problems but could not post them is distinguishable from a clean one. Background tasks are disabled, so the run cannot end, and the check pass, while its review agents are still working. The review action refuses to run on a pull request that edits its own workflow, so workflow changes land without an automated review and need a human read.

`claude-paper-review` reviews the scholarship of pull requests that change `paper.qmd`, `references.bib` or the project documents. It is advisory, not a required check, and skips fork pull requests, which receive no secrets. It opens the sources that changed sentences describe and checks that the prose reports them faithfully, then checks new bibliography entries, claim strength, the companion's claim register and the fit of the release label. Its method is K-Dense's peer-review, scientific-critical-thinking and citation-management skills at a pinned commit, applied through the `paper-pr-review` skill. Fetched pages and pull-request text can carry instructions, so the run is confined. It loads only user-scope settings, which keeps the repository's permission rules and skills out of it. Skills are installed without their `allowed-tools` grants, which would otherwise pre-approve their tools for the rest of a headless run, and the Skill tool is withheld so that no skill bundled with Claude Code can add grants either; the review reads the skills it names as files. WebFetch reaches only the hosts the bibliography cites and the lookup domains in `.claude/settings.json`, so a work cited only by DOI is usually checked against its abstract. Bash runs the `gh` commands that read the pull request and post comments, plus Claude Code's built-in read-only commands; every tool refuses reads outside the checkout except of the installed skills; and the job token can write only to pull requests. Background tasks are disabled, so the run cannot end while a subagent is still working. Pull-request authors stay trusted: the job runs the pull request's own workflow and bibliography, so a pull request sets its own review's fetch allowlist.

Secrets reach the narrowest job that needs them. The Cloudflare token serves only the site deployment, the Zenodo token only the Zenodo upload, and the Claude token only the Claude jobs. Dependabot-triggered runs see only Dependabot secrets, so a separate Claude token is provisioned there for reviews and nothing else. Fork pull requests receive no secrets.

Supply-chain defenses are layered. Every action is pinned to a full commit SHA. The release render installs a pinned TinyTeX release and the few TeX packages the paper needs beyond it, each verified against a committed SHA-256, and disables Quarto's render-time package installation; a published PDF's layout therefore changes only through a commit, and an upstream package revision fails the render until its checksum is updated. Dependabot proposes action and Python updates only after a 15-day cooldown, and those proposals pass the same gates as any other change. CI installs Python packages from the hashed, binary-only `requirements.lock` through `make setup`. The invariants require every pin in `requirements.txt` to match the lock, and Dependabot rewrites only `requirements.txt`, so its pip updates stay blocked until the lock is regenerated.
